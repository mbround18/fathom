# Research: Helm Mutate (006)

All findings below are grounded in direct reads of `src/protocol/v1/mutation.rs`, `src/protocol/v1/cmd.rs`, `src/protocol/v1/helm.rs`, `src/backend/helm.rs`, `ui/src/store/editSession.ts`, `src/backend/apply.rs`, `ui/src/components/ConfirmDialog.tsx`, `ui/src/components/panels/NodeActionsPanel.tsx`, and `Cargo.toml`.

## R1: The mutation.rs "guard" is a write-scope classifier, not a confirm/preview gate

**Decision**: New `BackendCmdV1` variants for Helm mutate (`PreviewHelmRollback`, `ApplyHelmRollback`, `PreviewHelmUpgrade`, `ApplyHelmUpgrade`, `UninstallHelmRelease`) each get an arm in `BackendCmdV1::mutation_target()` returning `MutationTarget::Namespaced { namespaces: vec![release_namespace] }` — the same classification `ApplyResourceYaml` uses when it carries a namespace.

**Rationale**: `mutation.rs:1-26` defines `MutationTarget { ReadOnly, Namespaced{namespaces}, ClusterScoped, Local, ContextSwitch{context} }` with `writes_cluster()` (line 36), consumed by an **exhaustive match with no wildcard arm on purpose** (module doc, lines 3-5: "adding a `BackendCmdV1` variant must force a decision here at compile time"). This is a compile-time-enforced write-scope/sandbox-routing guard used by `fathom-devbridge`, not a per-command confirmation mechanism — confirmation and preview are separate concerns handled at the frontend/command level (R2, R3). All five new Helm-mutate commands write cluster state scoped to the release's namespace, so `Namespaced` is the correct, precedent-following classification; there is no separate guard step to invent.

**Alternatives considered**: A new `MutationTarget` variant for "Helm release mutation" — rejected; the existing `Namespaced` variant already captures exactly this shape (single-namespace write), and inventing a new variant for no semantic gain contradicts the "force a decision, don't multiply cases" intent of the enum's exhaustive-match design.

## R2: Diff-preview follows 003's "compute preview client-side from already-fetched data, apply through one command" shape — generalized to two backend-supplied manifests

**Decision**: The backend computes and returns *both* manifest strings needed for a diff (current live manifest + target manifest) in a new `HelmMutationPreviewReady` event; the frontend renders the diff using the same diff-view component 003 built for YAML-apply, generalized to take two arbitrary manifest strings instead of "live YAML vs. edited YAML." No backend "diff" is computed server-side — text diffing stays a frontend concern, consistent with 003.

**Rationale**: `ui/src/store/editSession.ts` shows 003's diff-preview is a frontend state machine (`status: 'diffing' → 'applying'`, lines 21-22; `openDiffView()` marks the fetched `liveYaml` as reviewed, ~line 128) built entirely around data already on the client — there is no backend "preview" RPC in 003, only a single `ApplyResourceYaml` mutation (`cmd.rs:527`, handled by `src/backend/apply.rs::parse_and_validate_yaml` + `Api::<DynamicObject>::replace()` with `expected_resource_version` optimistic concurrency). For 006 this shape doesn't transfer 1:1 because, unlike YAML-apply (where both "current" and "proposed" are already on the client — the live fetch and the operator's edit buffer), rollback's target manifest and upgrade's rendered manifest are **not** already client-side: rollback's target is a specific historical revision's stored manifest (backend already holds it via `HelmRevisionSummary`/full revision fetch) and upgrade's target requires a fresh render (R4). So the backend must supply both sides once computed; the diff *rendering* itself stays frontend, reusing 003's diff-view component.

**Alternatives considered**: Backend computes and returns a structured diff (e.g. line-level hunks) — rejected; adds a new diffing dependency/format on the backend for no benefit when the frontend's existing diff-view already accepts two raw strings.

## R3: Confirmation pattern is named-item list, with typed-count only above a threshold — spec.md's assumption is corrected here

**Decision**: Uninstall (and the confirm step preceding rollback/upgrade apply) reuses `ui/src/components/ConfirmDialog.tsx` unmodified: a dialog naming the affected release by namespace/name, with `requireTypedCount = items.length > 5` (from `./action-utils`). Since every Helm-mutate confirmation acts on exactly one release, `items.length` is always 1, so **no typed-name/typed-count input appears** — this is a plain named-item confirm/cancel dialog, matching `NodeActionsPanel.tsx`'s explicit precedent that single-target destructive actions never require typed confirmation.

**Rationale**: `ConfirmDialog.tsx`'s header comment (lines 1-8) documents the typed-count behavior as conditional on `items.length > 5`; `NodeActionsPanel.tsx` (lines 3-5) explicitly calls out that node drain never requires typed-count confirmation for exactly this reason. **spec.md's Assumptions section (line 113) currently states uninstall should follow "the same deliberate-action affordance (e.g. typing the resource name)" — this does not match the actual codebase precedent.** The real precedent for a single-target destructive action is a named-item confirm dialog with no typed input. This research resolves that discrepancy in favor of the verified codebase convention; the plan and tasks that follow use `ConfirmDialog` as-is rather than inventing typed-name confirmation. (spec.md's assumption line is corrected to match, since Principle I only requires the dialog to *name* every affected object, not that the operator retype it.)

**Alternatives considered**: Require typed-name confirmation for uninstall specifically, as a deliberate escalation beyond the existing pattern (uninstall being more destructive than drain) — rejected for v1; not required by Constitution Principle I, adds a bespoke one-off confirmation UX inconsistent with every other single-target destructive action in the app, and can be added later as a scoped follow-up if operators report near-misses.

## R4: No Helm chart-template-rendering crate exists; rollback needs none, upgrade needs real Helm semantics

**Decision**:
- **Rollback** requires zero template rendering. `HelmRevisionSummary`/`HelmReleaseDetails` (`src/protocol/v1/helm.rs:44-51, 68-85`) already store each revision's `manifest: String` verbatim, decoded straight from Helm's own release-storage object (`src/backend/helm.rs` — "read directly from Helm 3's own release-storage Secret/ConfigMap objects, no `helm` binary shellout"). The rollback diff-preview is current-manifest vs. already-stored-target-manifest; the rollback apply reuses the same release-storage read/write path 005 already established for reads, extended to write a new revision entry pointing at the target's manifest (standard Helm rollback semantics: creates a new revision, does not delete intervening ones).
- **Upgrade** with genuinely new/edited values against the chart requires real chart-template rendering (Go-template syntax), and **no such engine exists in this Rust codebase today** — confirmed via `grep -n 'helm|tera|handlebars|gotmpl|minijinja' Cargo.toml` (zero matches). Hand-rolling a Go-template-compatible renderer in Rust for this feature is out of proportion to its scope and risks subtly wrong output (Helm's template functions, `.Files`, subchart handling, hooks). **Decision: shell out to the operator's local `helm` binary** (detected via `which helm` / `helm version` at feature-load time, mirroring how the rest of the app already treats optional external tooling as detect-then-degrade rather than a hard dependency) for the upgrade preview (`helm upgrade --dry-run` to obtain the rendered manifest without mutating anything) and the upgrade apply (`helm upgrade`) and for uninstall (`helm uninstall`), so all three write paths get Helm's own exact hook/template/dependency semantics instead of a reimplementation. If `helm` is not found on PATH, upgrade/uninstall report the FR-012 "clear, specific error" (chart source unreachable — the binary itself is the unreachable "source" in this case) and no mutation is attempted; rollback does not depend on the binary at all since it needs no rendering.

**Rationale**: This is a deliberate, scoped exception to 005's "no `helm` binary shellout" precedent, and is flagged in plan.md's Complexity Tracking: 005's precedent was specifically about **reads** (list/inspect), where a direct Secret/ConfigMap decode is strictly better (no external dependency, faster, works with Fathom's existing RBAC model). Mutation is different: `helm upgrade`/`helm uninstall` execute hooks, resolve chart dependencies, and handle atomic/rollback-on-failure semantics that only the real Helm implementation gets right; reimplementing that in Rust is a multi-month undertaking out of scope for this feature, and getting it subtly wrong is worse than a detected-optional-binary dependency. The backend still performs 100% of the actual mutation (Constitution Principle II — the frontend never talks to the cluster or invokes `helm` itself), so this preserves "One Contract, Backend Owns the Cluster."

**Alternatives considered**:
- A Rust Go-template-rendering crate — none exists in the ecosystem mature enough to match Helm's actual template functions and edge cases; rejected.
- Scope upgrade to values-only changes applied via a raw manifest patch (no chart re-templating at all) — rejected; this silently diverges from real Helm semantics (values referenced inside `{{ }}` blocks across many resources would not actually re-render), producing a preview that lies about what would happen — directly violates FR-004's "diff-preview shows what the upgrade would produce."
- Require the operator to have `helm` pre-installed as a hard prerequisite (fail feature-wide if absent) — rejected in favor of graceful per-action degradation (FR-012), consistent with how the rest of the app treats optional external tools.
